# Deterministic AI privacy

Approved local scope: backend projection, purpose-specific consent, scoped HMAC aliases, extension verification, CLI/MCP protections and tests. No production configuration, keys, migration, deployment or real-data model calls.

## Contract

- Canonical policy: `achievement-ai-v1`, backend-owned, implicit deny. The frontend exports its metadata as YAML; client `omitFields` may remove only controlled categories/types/months. Unknown fields and policy-weakening proposals fail validation.
- Source: authenticated member's saved Career Evidence records. Browser-only records are not uploaded or treated as server-verified. Only `source_matched`/`user_verified` items qualify.
- Allowed data: controlled skill categories, achievement-type enum, optional `YYYY-MM`, purpose-scoped subject/evidence references. Omit names, emails, handles, titles/descriptions, URLs, images, arbitrary skills, exact dates and future unknown fields.
- HMAC-SHA256 binds domain, key version, purpose, entity type and stable internal IDs through JSON tuple encoding. Names are not HMAC inputs. Dedicated 32-byte backend key; no identity/email secret reuse.
- Consent: `learning_recommendations` and `officer_assistant` default denied and remain separate from public achievement visibility/analytics. Platform model training stays disabled; third-party provider retention/training is controlled separately by that provider/account.
- Capabilities: random request ID, HMAC proof over owner/purpose/consent revision/expiry/payload hash, five-minute validity. Verification returns only the stored canonical filtered prompt. Raw frontend prompts are rejected independently by the extension. The fixed non-personal READY connection probe is exempt.
- Owner mapping: protected request row links subject alias to member ID. Owner-only context resolution never trusts a model-supplied member identity. Consent changes delete outstanding mappings; verification rechecks current role and consent.
- Officer AI: caller identity is aliased; approved views return counts only, with counts under five suppressed. Unreviewed raw skill/mail/website flows are blocked. Manual non-AI workflows remain available.
- CLI/MCP defaults use AI-safe views. `--human-raw` explicitly selects owner-authorized human CLI operations and is not exposed through MCP. This layer governs managed egress; it cannot prevent an authorized user or an external agent independently exporting owner-readable data.
- Privacy tickets/projections use non-spooled admission. No raw payloads, aliases, proofs, keys or names in application events; only operation/purpose/version/counts/outcome metadata.
- Original identity and owner-readable source records remain unchanged. Pseudonymization reduces direct identification; it is not an anonymity guarantee.

## Recovery and rollout prerequisites

Migration `0031_ai_privacy.sql` adds consent/request tables with member-delete cascades; its Git line ending is fixed to LF. Verify every previously applied migration checksum before a future Linux build/deployment. Preserve original historical bytes; never rewrite applied checksums to conceal a mismatch. Back up DB/binary/config before any later production rollout. Roll back code with its matching pre-migration DB snapshot.

Set `AI_PSEUDONYM_KEY_HEX` only on the backend, with `AI_PSEUDONYM_KEY_VERSION=k1`. Missing key disables projection; malformed configured keys reject startup. A key/version rotation changes aliases and invalidates capabilities. No key is generated by this local implementation.

Expired capability reads are denied immediately; expired rows are purged by the existing background maintenance cycle and on issuance. Consent updates, account deletion and a newer same-purpose request also remove prior mappings. In-flight disclosure already delivered to a provider cannot be recalled.

Dependencies reused: existing Rust `hmac`/`sha2`, SQLx/SQLite, frontend `yaml` 2.9.1, portal session/origin gateway and existing extension BYOK transport. Sources: [RustCrypto HMAC documentation](https://docs.rs/hmac/latest/hmac/), [OWASP sensitive-information disclosure guidance](https://genai.owasp.org/llmrisk/llm022025-sensitive-information-disclosure/).
